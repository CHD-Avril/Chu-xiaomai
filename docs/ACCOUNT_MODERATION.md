# 站内账号处理与通知

## 启用

在 `supabase-qq-participation.sql` 之后完整执行 `supabase-account-moderation.sql`，随后同时发布前端、QQ 后端和管理端。迁移保留账号、歌曲与票数，不向任何真实用户发布处理。已执行的迁移可重复运行，现有限制和处理记录不会被清空。后续重新运行旧 QQ 迁移后必须最后再执行本文件，恢复账号检查。

QQ 服务继续使用原有 AppID/AppKey/回调和服务器 Supabase Secret key，不需要新增密钥。发布的 `/qq/participation-health` 会额外校验 `qq_moderation_health()`，确认账号检查存在；缺少迁移或被旧迁移覆盖时，发布失败并回滚代码，不能以健康入口正常替代权限检查。

## 后台操作

「账号管理」列出已经通过 QQ 会话注册的站内账号，支持昵称和完整站内 UUID 搜索、分页。选择「处理账号」后可查看当前状态与最近 100 条记录，并发布：

- 站内警告：不限制操作，原因作为通知交付目标账号。
- 限制投票：禁止喜欢、点踩及取消投票，不影响投稿。
- 限制投稿：禁止新投稿，不影响投票。
- 封禁账号：同时禁止投稿与投票，保留登录、浏览和查看通知的能力。
- 恢复投票、恢复投稿、解除封禁：分别解除对应状态。解除封禁不会清除独立设置的投票或投稿限制。

限制支持 1、3、7、30 天或长期；限时处理由数据库服务器计算到期时间，到期自动失效，无需 cron。所有处理包括解除都须填写 1–500 字原因，原因会展示给目标账号。管理员身份从可信会话取得，不接受前端提交的操作人。账号状态版本防止多人编辑时静默覆盖；处理成功后重新读取版本再继续。

`account_moderation_actions` 保存完整处理历史，只有受保护的管理员 RPC 可追加；客户端包括管理员都不能直接修改或删除历史。记录同时写入现有运营日志。界面只展示最近 100 条，数据库保留完整记录。额度设置、征集结束、测试权限和歌曲锁定等规则仍独立生效。

## 用户通知与隐私

用户通过 HttpOnly QQ 会话访问自己的状态和通知，后端固定使用会话中的 AppID/OpenID，不信任前端传入的账号 ID。个人中心显示站内 UUID、生效中的限制和最近 50 条处理通知；其他页面会提示未读通知或参与权限受限。通知仅含处理类型、原因、时间与期限，不向用户暴露管理员邮箱和其他账号的资料。

标记单条或全部通知已读只影响当前账号，历史不会被删除。退出、会话过期或账号切换会清除本机旧账号资料，数据库中的限制与通知继续保留。状态在可见页面定期刷新，写入仍每次由数据库检查，因此篡改前端状态、清缓存和重登不能解除限制。账号限制适用于该站内 QQ 账号，不把多个 QQ 账号视为同一自然人。

## 验证与维护

`npm --prefix apps/admin run test:db` 使用隔离 PostgreSQL 验证角色权限、原因必填、处理历史、防伪造用户、独立限制、封禁/解封、自然到期、自己的通知、并发编辑以及升级覆盖检查。用户端自动测试验证网关固定身份、拒绝客户端处分指令和通知文本转义。不要在正式账号上发送测试警告或测试封禁。

全量歌单重建保留 QQ 身份、账号限制、通知和处理记录；解除处理必须经管理员操作并记录原因。数据库所有者仍具有维护权限，后台的防篡改控制不替代数据库备份或所有者权限管理。
